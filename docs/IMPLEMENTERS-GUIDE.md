# Implementers guide

For someone building a second implementation of KYA assessment semantics from the specification, in any language. The reference implementation is JavaScript. Two independent implementations passing shared vectors is the critical path to a credible standard ([work-stream WS3](WORLD-CLASS-PLAN.md)); this guide and the golden assessment vectors are the first piece of that path.

## What you are building

Pure functions over JSON, with no clock, network or state. Contract version 2 has nine; the first two are the assessment semantics, the next four are the building blocks under them, each testable alone, and the last three verify a credential and a score card (`interop/impl-contract/README.md`, [ADR-0034](adr/0034-conformance-contract-version-2.md), [ADR-0035](adr/0035-conformance-contract-credentials-and-score-cards.md)). An implementation may declare any operation `unsupported`; its vectors are then `not-run`, never `fail`.

1. `assess(manifest, profile, policy, evidence[], evaluatorDigest, now)` returns a `kya.assessment/v1` report. Selection, trust, scoring, blockers.
2. `checkCurrency(assessment, manifest, policy, incidents[], now)` returns a `kya.currency/v1` result. Change triggers and signed incident handling.
3. `canonicalize(text)` strictly parses one JSON text and returns its canonical text and SHA-256, or refuses. This is where the byte-level rules live (`docs/SPECIFICATION.md`, "Canonical form and strict parsing").
4. `digest(artifact, value)` returns the preimage and SHA-256 of a manifest, scope, profile, policy or of the signing input of a receipt or incident payload ("Digests and signing inputs").
5. `verify-envelope(kind, envelope)` returns `valid` and the key ID, envelope digest and signing input digest, or the code of the first failing step ("Envelope verification"). Validity is not trust.
6. `compare(left, right)` returns a comparison of two assessments or the first reason they cannot be compared ("Comparison of assessments").
7. `verify-credential(jwt, now, expectedIssuers, policy, statusLists, requireStatusCheck, report)` returns whether a `vc+jwt` assessment credential verifies, the ordered error codes, the issuer trust level and the status of each entry ("Credential verification"). A signature is never trust, and without the source report only internal consistency is claimed.
8. `verify-score-card(card)` recomputes a `kya.score-card/v1` from its embedded items and manifest and returns validity, the ordered problem codes and, for a valid card, the score and card digest ("Score card verification"). It needs the seeded bootstrap generator of that section.
9. `compare-score-cards(left, right)` compares two cards only when both are valid and share suite and evaluator digests.

Prerequisites you must also build: the bounded canonical JSON subset and SHA-256 digests (`docs/SPECIFICATION.md`, `evidence/golden-vectors.json`), strict JSON parsing, Ed25519 verification with the `kya.evidence/v1` and `kya.incident/v1` domain prefixes, and the record validators. Start with the existing byte and signature vectors in `evidence/golden-vectors.json` and with the `canonicalize` and `digest` vectors; they are the foundation for everything here.

## Build order that works

1. **Bytes.** Pass `evidence/golden-vectors.json` (canonical bytes, digests, signing input, incident vectors). If your digests differ, nothing above can match.
2. **Validators.** Manifest, profile, policy, evidence, incident: exact keys, identifier and timestamp grammars, list rules. Invalid top-level input is a refusal (non-zero exit); an invalid individual receipt is a rejection with a reason.
3. **Eligibility** per receipt, in the order of `docs/SPECIFICATION.md` "Trust and eligibility". Order matters because some receipts count toward run recency even though they are later rejected.
4. **Run selection**, duplicate quarantine, whole-run rules (`docs/SPECIFICATION.md` "Run selection and qualification", `docs/SCORING.md`).
5. **Scoring and gates**, then mandatory minimums, then blockers in the order the table in `docs/SCORING.md` lists them.
6. **Report assembly** and `reportDigest` (needed for byte-identical digests, not for decisions).
7. **Currency** and incidents.
8. Wrap it in the contract of [`interop/impl-contract/README.md`](../interop/impl-contract/README.md), run the harness, read failures from the first differing path.

Work from the written specification. Reading the JavaScript source is allowed, but then you have a derived implementation, not an independent one; say so when you report.

## Run the harness

```text
node scripts/run-vectors.mjs --impl "python3 my_impl.py" --name my-impl --language python --impl-version 0.1 --out report.json
```

Needs Node 22 and this repository. The summary is one JSON line: vector counts (pass, semantic-pass, fail, unsupported), the conformance summary and the first failing vectors with the first differing JSON path. The exit code is 0 only when every vector passed. Useful options: `--vectors FILE`, `--now ISO` (report time; default is fixed in the vectors file because the harness never reads a clock), `--timeout-ms N`, `--jobs N`, `--semantic-only` (ignore digests while you get decisions right).

To check the harness itself against the reference: `node scripts/run-vectors.mjs --impl "node interop/impl-contract/js-reference.mjs"`.

## Read the report

The output is a `kya.conformance-report/v1` (`docs/CONFORMANCE.md`) with evidence class `portable-vector`; executed IDs are vector IDs.

| Result | Meaning |
| :--- | :--- |
| `pass` | Every vector that cites this requirement passed, byte-exact. |
| `fail` | At least one vector citing it failed or crashed. |
| `not-run` | No vector cites it, a cited vector was unsupported, or you ran `--semantic-only`. |

Read `pass` narrowly. It means the published vectors for that requirement passed. It does not mean the requirement is fully implemented: a requirement that is cited by only a few vectors, or only by refusal vectors (which any non-zero exit satisfies), is thinly tested. The count of vectors per requirement is in the file. `not-run` is not a weaker pass; it stays in the denominator. Vectors cite only a subset of the requirements, so most requirements stay `not-run` by design: running the harness against the JavaScript reference (and against `interop/second-impl/`) gives 799 of 799 vectors passing, 60 of 284 requirements `pass` and 224 `not-run` (measured with `scripts/run-vectors.mjs`; before the credential and score card operations the same run gave 485 of 485 vectors, 39 `pass` and 219 `not-run` of the same 258; before contract version 2 it gave 272 of 272 vectors and 37 `pass`; the registry holds 284 requirements, so the 245, 247, 252 and 258 quoted in earlier texts were stale). The 21 requirements that moved to `pass` with the three newest operations are KYA-VCB-002 to 010, 012, 013, 014 and 016 and KYA-SCR-001 to 008. Read those narrowly: a requirement that mixes several rules is `pass` when the vectors that cite it pass, and some of its rules (credential export, status index assignment, the module import ban) have no vector, see `docs/fixlane14-integration.md`. (An earlier version of this guide said 31 of 211 and 180. Round 2 added 161 vectors and moved six requirements to `pass`: KYA-INT-001, KYA-INT-002, KYA-ENV-001, KYA-ENV-002, KYA-SCO-003 and KYA-RPT-005. Round 3, the four new operations, moved two more: KYA-INT-003, golden canonical bytes and signing input, and KYA-BND-003, comparison. A new vector may cite only a requirement already in the registry, so the other gains of round 3 are deeper coverage of requirements that already passed, not new passes.) The 224 that remain are not reachable through the six operations of the contract: they concern other operations (dossiers, credentials, capture, campaigns), the harness itself, or properties of the repository and its release process; `docs/fixlane13-integration.md` lists what the next operations would unlock. See the coverage table in [fixlane11-integration.md](fixlane11-integration.md). An `unsupported` reply to a vector of `assess` or `currency` whose expected result is a refusal is a `fail` (exit 0 is not a refusal); refuse with a non-zero exit instead. For a refusal vector of one of the four newer operations, the exact `unsupported` reply for that operation is `not-run`, so an implementation that predates contract version 2 loses nothing it had.

A `pass` for KYA-INT-001, KYA-INT-002 and KYA-ENV-002 covers only the part of the requirement that an `assess` input can express: member order, string escapes and duplicate members for INT-001 and INT-002 (not accessors, cycles or resource limits), and trust anchor keys for ENV-002 (the proof layer is covered by the Python checker and the strictness tests, not by a vector). Read those three as partial.

The report is unsigned and self-run. Anyone can run the harness on themselves, edit the output or run a different binary. A claim of conformance is credible only when a third party reruns the harness on the exact released implementation and publishes the report, ideally signed with `signReport`.

## The vector file

`evidence/assessment-vectors.json` (`kya.assessment-vectors/v2`, with a `contract` member naming version 2 and its nine operations) holds 799 deterministic vectors: 212 `assess`, 60 `currency`, 72 `canonicalize`, 38 `digest`, 68 `verify-envelope`, 35 `compare`, 223 `verify-credential`, 72 `verify-score-card` and 19 `compare-score-cards`, of which 275 are refusals (109 of the 314 vectors added for the three newest operations, 35 percent). The 485 vectors of the first six operations are unchanged byte for byte (their combined digest is pinned in `test/contract-credential-score.test.mjs`, and the 272 of the first two in `test/contract-operations.test.mjs`). Each has `id`, `description`, a one-line `rationale` tied to the requirement it tests, the cited `requirements`, complete `inputs` (or, for nine vectors, `rawInput`, see below) and the `expected` result. Keys are public synthetic Ed25519 keys derived from published seeds. Times are fixed. Regenerate with `node scripts/assessment-vectors.mjs`; `--check` fails on drift. The generator also holds a hand-written claim per vector and refuses to write if the reference disagrees, so the file is not only a snapshot of the code. A claim is never edited to match the reference. In round 2 the reference disagreed with a hand-written claim in two vectors: one was an arithmetic mistake in the claim (coverage 0.6, not 0.7), and the other exposed an unwritten rule (a receipt from a revoked key still counts toward the run's issuer set), which is now written down and pinned by vectors.

`rawInput` is the exact stdin text of a vector whose input cannot be held as a JSON value in the vectors file, such as duplicate object members, a `__proto__` member, text after the object, or an indented input with escaped text. A vector carries exactly one of `inputs` and `rawInput`. An empty `reasonContains` in an expected rejection means the specification gives no wording for that reason (a malformed receipt, a non-canonical key spelling): any non-empty reason text is accepted, and the vector still checks the record's index and `id` (null when the record never passed validation).

Coverage in the file: every blocker code except `NO_OBSERVED_CHECKS` and every currency trigger code. Scenario families: mandatory minimums (pass, fail, omitted, abstain, independent-pass, declaration, stacking, older run, rejected receipt, error outcome, policy order), principal binding (declared kinds, added or changed after signing, malformed declarations), revoked key, subject and evidence, expiry, ambiguity between tied runs (two and three runs), cross-run cherry-picking, which receipts count toward run recency, duplicate evidence IDs (within a run, across runs, with an expired copy), declaration laundering, fixture versus runtime, capture-issuer rejection, critical failures, empty evidence, blocker order and short circuits, score floor and coverage rounding, rejection reason precedence for every reason in the specification's list, public key spelling and point strictness (as proof key and as trust anchor), member order, string escapes and number spellings, duplicate and prototype members, unknown fields, identifier, hash, text and timestamp grammars, numeric ranges and enumerations of every record, and incidents (open, resolved, appealed, ambiguous, untrusted, revoked key, other subject, duplicate delivery, future dated, invalid record, reason order, severity, delivery order).

Round 2 (161 vectors) by area, with the number of refusals in parentheses: blocker order and short circuit 8 (0), scoring arithmetic 4 (0), run selection and run rules 22 (0), rejection reason order 12 (0), envelope key strictness 26 (17), canonical form and strict parsing 11 (7), field rules and grammars 28 (28), receipt shape 4 (0), principal binding 11 (7), mandatory minimums 10 (5), incidents and currency 25 (7). Refusals are 71 of the 161 new vectors. The areas are assigned by vector ID pattern, so treat the split as approximate; the totals are exact.

Round 3 (213 vectors, contract version 2), refusals in parentheses: `canonicalize` 72 (45): member order including UTF-16 code unit order for names outside the Basic Multilingual Plane, escapes, number spellings and the shortest round-trip form, and refusals for duplicates, the three refused names, grammar violations, the safe integer bound, depth 33 and an unpaired raw surrogate; `digest` 38 (21): subject, scope, profile, policy and the two signing inputs, field changes that must change the digest, and invalid records that have none; `verify-envelope` 68 (5): every failure code in order, eight key spellings, four point strictness cases, signing domain confusion, a scalar `S + L` malleation and key substitution, and valid envelopes from keys no policy trusts; `compare` 35 (12): comparable pairs, each of the eight reasons, and refusals of tampered, legacy and malformed reports. Every `MUST NOT` the new vectors cite (INT-002 duplicates and prototype names, BND-003 equal scope names with different purpose or permissions, ENV-001 and ENV-002 key spellings and small-order keys) has at least one vector in which the forbidden behaviour is attempted and must not happen. A same-team second implementation passed all 205 of the first batch on its first run with no disagreement; see "Second implementation findings" for what that does and does not show.

Round 4 (314 vectors, still contract version 2, [ADR-0035](adr/0035-conformance-contract-credentials-and-score-cards.md)), refusals in parentheses: `verify-credential` 223 (79): the 21 opening steps in order, each header and token form rule, the issuer `did:key` rules including small-order and off-curve keys, signature tampering including `S + L`, the claim rules with fixture laundering, binding to the source report, policy trust and the status list check; `verify-score-card` 72 (22): valid cards and each tamper class including re-sealed edits, the floor and the order of problems; `compare-score-cards` 19 (8). 32 of the refusals are text the strict parser refuses. The text was written first, then the vectors; the second implementation was written by a separate agent session from the specification and the contract README only. It passed 308 of the first 309 vectors on its first real run, and the one miss and five questions it reported became specification sentences (`docs/fixlane14-integration.md`). That shows the text was nearly enough for a same-team reader, not that it is complete.

## What the vectors do NOT cover

Be explicit; a green run is silent on all of these.

- **Runtime capture.** Whether the evidence came from a real observation of the agent (ADR-0017 capture, campaign ledger, adapters).
- **Truthfulness.** A valid signature proves bytes and key possession. No vector shows an issuer told the truth or was independent.
- **Privacy.** Redaction, minimisation, retention, selective disclosure.
- **Performance and resource limits.** Bounds on size, depth and time beyond the harness limits. Denial of service, memory and timing behaviour are untested.
- **VC bridge** (`docs/VC-BRIDGE.md`), **campaign ledger**, **scenario suites and holdouts**, dossiers, universes, dashboard, CLI, GitHub Action.
- **Verification-only entry points** such as `verifyAssessment` as a standalone operation (it is exercised indirectly by the currency refusals and by the `compare` refusals). Comparison is covered by `compare`, envelope checking by `verify-envelope`.
- **Size limits.** A 1 MiB input is too large to commit, so the input size bound and the 100000 value bound of the strict parser are not exercised by a vector (the repository tests one size case against both adapters). Number formatting and string escaping agree between the reference and the second implementation by construction, because both are JavaScript on one runtime; an implementation in another language is the real test of those rules.
- **Report fields not compared individually.** Dimensions, limitations text, accepted evidence digests and blocker text are covered only through `reportDigest`, so a mismatch there is reported at `$.reportDigest` without a finer path. Use `--semantic-only` to separate decision bugs from layout bugs.
- **Memorisation.** The vectors are public and fixed. An implementation could return stored answers keyed by input. Credibility needs independent review of the source and, later, private held-out vectors; neither exists today.
- **Independence of the expected values.** They come from the JavaScript reference, cross-checked against hand-written claims by the same authors. Two implementations that agree on a vector prove consistency, not correctness against intent.
- **Unreachable code.** `NO_OBSERVED_CHECKS` cannot be produced by any input (qualification needs known weight above zero, which needs at least one selected check). It is listed under `unreachableBlockerCodes`; you need not emit it.

## Spec gaps found while writing the vectors

These are behaviours the vectors pin that the prose specification does not state. Treat them as open questions for the editors, not settled rules.

1. **Tie-break among equally recent runs.** The reference prefers a run with a failed critical check, then the smaller run ID, and reports it as `selectedRunId` even when ambiguous.
2. **Rejection reason strings** are free text in the reference. The vectors treat 22 assess reasons and 12 incident reasons as exact strings because they feed `reportDigest`. A reason code vocabulary would be a better interface.
3. **Error text for malformed envelopes** is implementation specific; those vectors match a keyword and carry no digest.
4. **Within-run conflict handling.** A repeated check keeps the most conservative outcome, then the earlier observation, then the run cannot qualify.
5. **Evidence mode** is `none`, `runtime`, `fixture` or `mixed`, and the fixture limitation string is part of the digest.

Round 2 found more. Items 6 to 13 were unwritten rules that the reference enforced and that the second implementation got wrong or had to guess; each is now written in `docs/SPECIFICATION.md` or `docs/SCORING.md`, pinned by vectors, and implemented in the second implementation from that text. They are still same-team readings of the text.

6. **The dimension list.** An assessment always lists the six fixed dimensions in order, with zeros for a dimension no check uses (`docs/SCORING.md`). The second implementation listed only the dimensions its profile used, so four scoring vectors disagreed on `reportDigest`.
7. **Field rules.** Identifier, text-length, range, enumeration and containment rules for every record were enforced but unwritten (`docs/SPECIFICATION.md`, "Field rules"). The second implementation accepted agent IDs starting with a hyphen, with spaces or of 129 characters, duplicate tool IDs, an approval permission outside the scope, a trust anchor ID that is not the key fingerprint and an unknown dimension.
8. **Which receipts the run rules see.** The issuer, repeated-check and duplicate-ID rules are evaluated over the bound receipts, including those later rejected as revoked, expired or stale. The second implementation evaluated them over the survivors, so it missed `MIXED_RUN_ISSUERS`, `REPEATED_RUN_CHECKS` and `RUN_CONFLICT` in six constructed cases.
9. **Reason precedence outside the selected run.** Revocation, expiry and freshness reasons apply to receipts of older and tied runs too, ahead of `Older run excluded`. The second implementation reported the run exclusion.
10. **Duplicate IDs across runs.** An evidence ID reused in another run is quarantined; the second implementation only looked inside the selected run.
11. **`RUN_INVALIDATED` and quarantined duplicates.** The code table said revoked, expired or stale; the reference also raises it for a quarantined duplicate in the selected run. The table now says so.
12. **Run recency** is the latest observation time among a run's bound receipts, and runs tie when those times are equal. Both implementations already agreed; the text was silent.
13. **`blockerCodes` cross-checks.** A code list may not contradict its report: unknown codes, a list that disagrees with the number of failed critical checks, or codes on a qualified report are refused. The second implementation checked only the length.

Open and not pinned by any vector: the wording of the reasons for malformed receipts and incidents (free text by design); input size and nesting limits (the 4 MiB input bound and the 1 MiB output bound of the contract are not exercised by a vector); a byte order mark, lone surrogate escapes and Unicode normalisation of text; number spellings beyond those the Python checker supports (the Python checker declares a smaller portable numeric subset and refuses values such as 0.8); and the tie-break used to report `selectedRunId` among tied runs.

## Reporting disagreements

A disagreement is a vector where your result differs from `expected`, or a requirement you believe is mis-specified. Do not edit the vectors to make your implementation pass.

1. Re-run the failing vector alone (`--vectors` with a one-vector file) and keep the harness output, including the first differing path.
2. Decide which side is wrong by reading the cited requirement and the vector rationale. If your implementation is wrong, fix it.
3. If the vector or the specification is wrong or ambiguous, open an issue with the vector ID, the requirement ID, both outputs and your reading of the text. Do not describe the reference as correct merely because it exists.
4. Resolutions are recorded in an ADR and, if semantics change, in a new vector with a regression test; a change to evaluator or protocol follows `AGENTS.md` (substantive ADR, adversarial regression, a test that detects the weakened gate).
5. Report an implementation that crashes or hangs on a vector as a failure, not a skip.

## Claiming conformance

State: the implementation name, version and source digest; the vectors file digest; the harness version; the full report; and which requirements are `not-run` and why. Do not claim conformance to the standard, to Open-KYA, W3C VC, A2A or MCP, or independent review. A passing run claims only that those published vectors passed.

## Second implementation findings

A team-built second implementation (`interop/second-impl/`, not independent, written without reading the reference source) matches the decision and every semantic field of all 799 vectors and now matches all 799 byte for byte. On the first 111 vectors it first matched 43 byte for byte, then 79, then all 111. The documented text then closed the digest gap for those 111: the blocker wording strings, the full `kya.currency/v1` result layout, the `evidenceBundleDigest` definition, the reason vocabulary for rejected evidence and ignored incidents, the blocker short circuit, future-dated recency, and the validator grammars (see `interop/second-impl/AMBIGUITIES.md` for the vector-level table). The blocker wording and ordering are in `docs/SCORING.md`; the currency result layout, reason vocabularies, validator grammars and future-dated recency rule are in `docs/SPECIFICATION.md` ("Currency result layout and reason vocabulary"). Round 2 then added 161 vectors written from the text before the reference was consulted. Run against the final vector file, the second implementation as it stood before round 2 failed 26 of the 161 new vectors (four dimension digests, nine field rule refusals, six run rule cases, five reason precedence cases and two blocker code checks; items 6 to 13 above), while the reference passed all 161. Each disagreement was resolved by writing the missing rule down and by fixing the second implementation against the written text, never by editing an expected value. That shows the text is sufficient for this vector set, not that it is complete or that the implementation is independent; choices no vector pins remain guesses (see `interop/second-impl/AMBIGUITIES.md`).

Round 3 (contract version 2). The specification text for the four new operations was written first, then the vectors, then the second implementation was extended by a separate agent session that was told not to read the reference source, the operation module, the generator or the expected values of the new vectors before its first run. Result of that first run: all 205 vectors of the first batch passed with no disagreement, and so did the eight incident vectors added afterwards. Read that narrowly. It means the text and the contract README were enough for a same-team reader to rebuild the reference output on these vectors; it does not show the text is complete, and the two implementations are both JavaScript on one runtime, so number formatting, string escaping and Ed25519 verification agree partly by construction. The honest findings were elsewhere: (1) the specification gave no field rules for an incident payload, which `digest` and `verify-envelope` need, and the second implementation had to guess them (the guess happened to match; the rule is now in the "Field rules" paragraph with eight vectors); (2) the second implementation's stdin parser did not follow the text it was meant to follow: it refused only one of the three prototype member names, allowed depth 64 instead of 32, had no value count or size bound, and decoded ill-formed UTF-8 leniently; (3) the contract README said input of up to 4 MiB while the reference already refused above 1 MiB, now stated and tested against both adapters; (4) three smaller silences (the type of a check status in a comparison, whether `blockers` must be an array when `blockerCodes` is present, whether a mandatory minimum name is checked when a policy is only digested) are now written down. None was resolved by editing an expected value.

## Public key strictness

A proof or trust-anchor key has exactly one accepted spelling: `-----BEGIN PUBLIC KEY-----`, a line feed, the 60 base64 characters of the 44-byte Ed25519 SPKI (canonical padding bits, no line wrapping), a line feed, `-----END PUBLIC KEY-----` and a final line feed. CRLF, re-wrapped lines, a missing final newline, blank lines, non-canonical trailing base64 bits, long-form DER lengths and bytes after the SPKI are all refused. The 32-byte key must also decode as an Ed25519 point (RFC 8032 section 5.1.3): a non-canonical `y`, a point off the curve, a non-canonical `x` sign and any small-order point (8P is the identity, so the identity key with signature `01` followed by zero bytes would otherwise verify any payload) are refused. The JavaScript core, `interop/second-impl/` and `interop/python/` now all apply this rule, each with its own point arithmetic (neither the second implementation nor the Python checker imports `src/`). `test/second-impl-strictness.test.mjs` feeds all three the same 60 or more mutated envelopes and requires the same accept or reject decision; the Python checker works at the proof byte layer only, so payload-schema mutations are outside that comparison. These are same-team implementations, so this shows the text is enough to build the rule, not independent confirmation.
