# ADR-0022: W3C VC 2.0 export bridge for assessment results

**Status**: Implemented
**Date**: 2026-10-14
**Depends-on**: ADR-0002, ADR-0003, ADR-0013, ADR-0016

Review boundary: separate project lane; no external certification, no external VC verifier library was run against the output.

## Context

A `kya.assessment/v1` report carries an unauthenticated checksum (`verifyAssessment` returns `authenticated: false`), and evidence receipts use a project-specific envelope. Relying parties in the wider identity ecosystem consume W3C Verifiable Credentials. The W3C VC Data Model 2.0, Bitstring Status List v1.0 and (per the page fetched) VC-JOSE-COSE are Recommendations; DIF hosts a KYA-OS task force (research note `docs/research/2026-10-14-kyc-to-kya-controls.md`, not re-fetched here). Exporting KYA results in that format is useful only if the honesty limits survive the trip: an assessment is not an authorization grant, a fixture result must never look like runtime evidence, and a valid signature proves key possession, not truthful execution.

## Decision

1. New package `src/vc-bridge/` (zero dependencies, `node:crypto` and `node:zlib` only) exports an assessment as a VC 2.0 document secured as a compact JWS: header `alg: EdDSA`, `typ: vc+jwt`, `cty: vc`, `kid` the issuer did:key verification method; the payload is the bare credential (no `vc` claim).
2. The issuer is a `did:key` of the Ed25519 public key (multicodec 0xed01 plus multibase base58btc `z`), implemented locally and tested against two published did:key strings.
3. `credentialSubject` identifies the agent by `urn:kya:subject:sha256:<subjectDigest>`. It carries decision, score, coverage, independent coverage, profile, policy and evaluator digests, the report digest, `evidenceMode` copied verbatim from the report, blocker codes (`null` for legacy reports that lack them), the limitations list verbatim, and a fixed `notAsserted` list. It carries no principal, agent name or person identifier. An `evidence` entry of type `KyaInputDigests` references the exact bundle, accepted-evidence and input digests.
4. The exporter verifies the report digest first and refuses a report whose `evidenceMode` and fixture limitation disagree. The verifier refuses a credential where they disagree. That catches an edit of `evidenceMode` alone, but not an edit that also deletes the fixture limitation and is re-signed by the key holder; that case is caught only when the caller supplies the source report (`report` option), which triggers a field-by-field comparison (`REPORT_MISMATCH`). The exporter accepts no option that overrides `evidenceMode`.
5. Validity: `validFrom` defaults to `assessedAt` and may not predate it; `validUntil` defaults to, and may not exceed, the assessment's own `validUntil`.
6. `verifyAssessmentCredential` (an optional `report` adds the source-report comparison) checks, in order: token shape (strict base64url, three segments), `alg` is exactly `EdDSA` before any key is touched (none, HMAC, and every other value refused), header members limited to `alg typ cty kid` (no `jwk`, `jku`, `x5u`, `x5c`, `crit`), `typ` `vc+jwt`, `kid` equals the issuer did:key method, Ed25519 signature, context and type, KYA claim consistency, validity window at an explicit `now`, optional expected issuer keys, optional policy anchoring. The result always has `authenticated: false` and a warning. Issuer trust is `unchecked`, `expected` or `anchored` and is policy-relative.
7. Revocation uses a W3C Bitstring Status List: `BitstringStatusListCredential` secured the same way, minimum 131,072 entries, GZIP then multibase base64url with prefix `u`, index 0 the leftmost bit, purposes `revocation` and `suspension`, mandatory `validUntil` and optional `ttl` (a stale or no-expiry list is refused as `STATUS_LIST_EXPIRED` or `STATUS_LIST_NO_EXPIRY`). `checkStatus` applies the spec checks (entry type, purpose match, minimum length, range) and bounds decompression at 2 MiB by default because the specification sets no ceiling.
8. Index assignment is keyed and deterministic: `HMAC-SHA256(secret, "kya.vc.status-index/v1\n" purpose "\n" reportDigest "\n" counter) mod size`, probing the counter upward past indices already in the issuer ledger. The index is per credential (keyed on the report digest, not the subject digest), so a list reader cannot map an index to a subject without the secret. A credential is marked revoked when its subject digest is in `revokedSubjectDigests` or any evidence ID it selected is in `revokedEvidenceIds`. Suspension has no KYA policy source; the caller names the subject digests.
9. Raw Ed25519 keys (did:key decode, issuance, JWS verification) are validated with a BigInt point decode and a cofactor check; non-canonical, off-curve and small-order keys are refused. Policy input to revocation mapping goes through `validatePolicy`.
10. Canonicalization for the JWS bytes is KYA canonical JSON (sorted keys) used only to make export deterministic. This is not RFC 8785 JCS and no Data Integrity or JCS compatibility is claimed.

## Alternatives

W3C Data Integrity (for example `eddsa-jcs-2022`) would put a proof inside the document, but it requires RFC 8785 JCS or RDF Dataset Canonicalization. KYA canonical JSON differs from JCS in number formatting and string ordering rules, and RDFC needs a JSON-LD processor, which this zero-dependency project does not have; claiming it would be false and a subtly wrong canonicalization is a silent verification failure. JOSE keeps the signed bytes exactly the bytes transmitted. SD-JWT selective disclosure was not needed: the credential is intentionally public-safe, digests only. `did:web` or a registry would add network resolution and an operator; `did:key` is self-resolving and offline, at the cost of no key rotation or revocation of the identifier, which policy anchors and status lists handle instead. An index derived by plain hashing of the subject digest lets anyone who holds a candidate digest test whether it appears among the set bits; a keyed per-credential index removes that. Sequential indices were rejected because the spec asks issuers to assign indexes randomly. A single list for both purposes is not allowed by the model (one purpose per credential in this implementation), so there are two lists.

## Consequences

KYA results can be carried and checked offline by software that understands VC-JOSE-COSE and Bitstring Status List, with the fixture and limitation fields intact. Cost: the issuer must keep a ledger (report digest, subject digest, selected evidence IDs, assigned indices) and a status secret, and must republish status lists on policy change; verification of status is only as fresh as the list supplied. Claim ceiling: a valid credential shows that the holder of an Ed25519 key signed these bytes within a validity window and that a supplied status list did not mark it. It does not show human identity, an authorization grant, truthful execution, independent review or that the issuer is trustworthy. The inline context uses a URN vocabulary that cannot be dereferenced and no JSON-LD processor or third-party VC verifier was run, so JSON-LD interoperability is unverified. The did:key vectors are two published strings checked for decode, multicodec and canonical re-encode; the specification page did not publish raw key bytes alongside them. The VC-JOSE-COSE page fetch was truncated, so its `kid` and algorithm sections were not read.

## Validation

`test/vc-bridge.test.mjs` covers: did:key vectors, base58 edge cases, export and verify round trip, header shape, subject privacy (no principal or name), evidence digest references, deterministic export, fixture and mixed and runtime modes, a mode-only forgery rejected, a mode edit with the limitation deleted and re-signed shown to pass without the report and to fail with it, refusal of tampered reports, payload, header and signature tampering, alg none, HS256 and eleven other algorithm spellings, forbidden header members, wrong signing key, expired and not-yet-valid windows at exact boundaries, expected-issuer and policy anchoring with revoked key, strict token shape, bit order and encoding round trips, wrong prefix and padding and corrupt gzip, a 64 MiB gzip bomb and an explicit ceiling, undersized lists, lists without or past `validUntil` or `ttl`, small-order, identity, non-canonical and off-curve keys and the identity-key forgery, policy and ledger validation (including the CLI refusing an empty policy), wrong and out-of-range indices, purpose mismatch, suspension lifting by republishing, list issuer and window checks, keyed deterministic index assignment, collision probing that never moves earlier entries, KYA revocation to ledger mapping, and end-to-end status checks. The CLI was run for real and its outputs are recorded in docs/VC-BRIDGE.md. Ten single-point mutations were applied to disposable edits of the source and each is detected by the suite: accept any alg, skip the `kid` match, skip the evidence-mode consistency check at export and at verify, drop the decompression ceiling, flip the bit order, skip the minimum length check, make the index ignore the credential, skip expiry, skip not-yet-valid. The first run missed two of these (the `kid` match, because a header edit already breaks the signature, and the credential-dependence of the index); tests were added for both.
