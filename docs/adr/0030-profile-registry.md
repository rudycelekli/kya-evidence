# ADR-0030: Profile registry and metadata rules

**Status**: Proposed
**Date**: 2026-10-14
**Depends-on**: ADR-0003, ADR-0016, ADR-0023, ADR-0024

Review boundary: written and tested by the authoring lane only. No maintainer review, no domain-expert review of any profile, no external adoption.

## Context

Scoring is measured against one frozen profile, and policies and evidence bind it by digest. The code validates a profile's shape (`validateProfile`), but nothing says how a profile is named, versioned, retired or described, what it may claim, or how the repository lists the profiles it ships. The extension registry draft (`docs/governance/EXTENSION-REGISTRY.md`) names profiles as an extension kind but has one row for the core profile, listed under the file name `core-v1` while the document id is `kya-core`. The work-stream plan (WS2) calls for flagship profiles that domain experts accept; without a registry, a draft profile and an accepted one would look the same.

## Decision

1. `docs/PROFILES.md` specifies profile validity (citing the enforcing code), digest identity, versioning and freezing, naming and namespacing, required metadata, what a profile may not claim, and deprecation.
2. `evidence/profile-registry.json` (`kya.profile-registry/v1`) lists every profile file in `profiles/` with its canonical digest, counts, status, purpose, intended scope, known gaps, change log and owner placeholder. It is generated by `scripts/profile-registry.mjs`, which computes digests through the existing code, refuses a profile file with no metadata, refuses a policy template whose target profile is unregistered, and has a `--check` mode for drift.
3. `src/profiles/validate-metadata.mjs` validates metadata and the registry and fails closed. It lives outside `src/conformance/`, so the evaluator identity is unchanged; the reference profile file is unchanged.
4. Status is `draft`, `reference`, `deprecated` or `retired`. There is no approved or certified status. `signOff` is `null` in every entry; a non-null record needs reviewer, role, date and an evidence digest and is refused on a draft. Prose claiming review is refused when no sign-off record exists.
5. Project ids are `kya-core` and `core-<name>`; third-party ids are `<dns-namespace>:<name>`; reserved prefixes follow the extension registry. The registry uses the document id (`kya-core`), not the file name.

## Alternatives

Put profile metadata inside the profile file: rejected, the profile schema is exact-keyed and frozen, and any change alters digests and the evaluator identity. A status for expert-accepted profiles now: rejected, no such review exists and the status would invite false claims; it can be added by a later ADR when evidence for a review exists. Verify sign-off truth in the validator: not possible offline, so it checks form only. Hand-written digests in the registry: rejected, they would drift; the generator recomputes them.

## Consequences

A reader can see which profile exists, which bytes it is, what its limits are and that nobody has reviewed it. Adding a profile file requires metadata, a registry regeneration and a change log, so freezing is visible in review. The validator cannot show that a profile is good; a well-formed entry is not an endorsement. Registry rules are not yet linked to specification requirements, package scripts or CI; proposals are in `docs/lane-u-integration.md`. Once flagship profiles exist they enter as `draft` and stay there until a sign-off record with evidence is added by a maintainer.

## Validation

`test/profiles.test.mjs` covers the committed registry against the generator, digests recomputed from the real profile file, and negative cases: digest mismatch, duplicate id and version, same digest under two ids, missing known gaps, unevidenced sign-off claims, unknown status, bad owner contact and naming. `npm test` and `npm run check` pass in the authoring lane. No independent review has run.
