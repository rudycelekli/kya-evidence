# ADR-0026: Golden assessment vectors and a language-neutral harness

**Status**: Implemented
**Date**: 2026-10-14
**Depends-on**: ADR-0003, ADR-0008, ADR-0013, ADR-0014, ADR-0015, ADR-0016

Review boundary: implemented and tested in this repository by the authoring lane only; no independent review, no second implementation has run these vectors, no external certification.

## Context

The roadmap's critical path to a credible standard is two independent implementations. Today only bytes and signatures have portable vectors (`evidence/golden-vectors.json`, ADR-0008). The assessment semantics have none: run selection, eligibility, trust and revocation, scoring, mandatory minimums, blocker codes, principal binding, currency triggers and incident handling are defined by prose and by the JavaScript reference, so an outside implementer cannot tell whether a different answer is a bug in their code, a bug in the reference or an ambiguity in the text. ADR-0015 defines a conformance report, but it can only be filled by tests inside this repository.

## Decision

1. `evidence/assessment-vectors.json` (`kya.assessment-vectors/v1`) holds 272 deterministic vectors, 212 for `assess` and 60 for `currency` (111, 76 and 35 when this ADR was accepted; fix lane 11 added 161, see the update below). Each has an ID, description, rationale tied to a normative requirement, the cited requirement IDs, complete inputs and the expected result: decision, score triple, coverage, independent coverage, blocker codes, selected run, per-check status and independence, rejected evidence with reasons, and the canonical report or result digest. Eighty-three vectors expect a refusal (twelve when accepted).
2. Signing keys are public synthetic Ed25519 keys derived from SHA-256 of published strings; times are fixed ISO strings; no clock is read.
3. `scripts/assessment-vectors.mjs` builds the file only through `src/index.mjs`, runs twice and refuses to write if the runs differ. Every vector also has a hand-written claim in the generator; the generator refuses to write if the reference disagrees, so the file records what the specification says and not merely what the code does. `--check` fails on drift. It is not wired into CI by this change.
4. `interop/impl-contract/README.md` defines the contract: an implementation is one command that reads one `kya.impl-input/v1` object on stdin and writes one `kya.impl-result/v1` object on stdout; a non-zero exit is a refusal or crash. `js-reference.mjs` implements it with the reference.
5. `scripts/run-vectors.mjs --impl "<command>"` runs every vector with a timeout and size bounds, compares key for key and reports the first differing path. It emits a `kya.conformance-report/v1` with evidence class `portable-vector` and vector IDs as executed IDs: a requirement is pass only if all vectors citing it pass, fail if any fails, not-run otherwise, and unsupported operations are not-run. The harness does not give the implementation the vector ID or expected value and does not trust its claims about itself.
6. Comparison rules: normative reason strings are exact; failures that occur before a record can be interpreted (bad signature, key mismatch, malformed envelope, invalid incident record) carry a lowercase `reasonContains` keyword and no digest, because their error text is implementation specific; `--semantic-only` ignores digests but can never record a pass.
7. `docs/IMPLEMENTERS-GUIDE.md` says how to build and run an implementation, how to read the report, what is not covered and how disagreements are reported.

## Alternatives

Digests only, with no field-level expected values: rejected, a mismatch would not say which semantic differs. Field-level expected values only: rejected, they cannot prove the full canonical report including layout. Expected values taken from the reference without independent claims: rejected, the file would be a snapshot that cannot disagree with the code; the generator claims are a cheap guard. Compare reason strings by keyword everywhere: rejected, the reasons feed the report digest and a stable reason vocabulary is better fixed by the editors than left loose. A stable reason code vocabulary now: deferred, it changes the report format and the evaluator and needs its own ADR. Vectors expressed as shell commands or per-language test files: rejected, a single stdin and stdout contract works for any language. A live service the implementer calls: rejected, offline and reproducible is the point. Adding `verify-assessment` as a third operation to reach `NO_OBSERVED_CHECKS`: rejected, it would test a validator accepting a code, not an input producing it.

## Consequences

An outside team can measure itself against the assessment semantics without reading the reference source. Ambiguities now have names: the vectors pin a run tie-break, exact reason strings and a report layout that the prose does not fully state; they are listed in the guide as spec gaps for the editors. `NO_OBSERVED_CHECKS` cannot be produced by any input and is declared unreachable. The vectors are public and fixed, so they can be memorised; they are not a certification, a security audit or evidence of independence, and expected values come from the same authors as the reference. A pass means the published vectors for a requirement passed, not that the requirement is fully verified, and a requirement cited only by refusal vectors is thinly tested. Any later change to the reference evaluator that changes an expected value will fail the drift check and needs an ADR and a deliberate regeneration; this makes protocol drift visible. The file is about 1.5 MB. Shared integration (package scripts, CI, registry entries) was deferred to the integration owner (the working note, which was not retained, is not part of the repository).

## Validation

`test/assessment-vectors.test.mjs`, no network and no model. The generator reproduces the committed file byte for byte; vector IDs are unique and every cited requirement exists with a rationale naming it; every blocker and currency code is exercised or declared unreachable; the named scenario families are present. The JS reference passes all 111 vectors through the harness CLI and the report validates against the registry. Five deliberately weakened copies of the reference (capture-issuer gate, declaration gate, mandatory minimums, ambiguity gate, critical-failure gate), each made in a temporary directory, fail named vectors and leave the requirement fail, never pass. Tampering a decision, score, digest, incident list or reason keyword in an expected value is detected with the first differing path. The harness records no pass for oversize output, non-JSON, duplicate JSON members, a crash, a non-zero exit, a hang, a missing binary, an answer where a refusal is expected, an extra, missing or wrong field, or an unsupported operation, and requirement results follow the all-vectors rule. Not validated: any second implementation, external review, behaviour on hostile or very large implementations beyond the stated bounds, and whether the semantics are the right ones.

## Update (fix lane 11)

The set grew to 272 vectors. Nine vectors carry `rawInput` (the exact stdin text) instead of `inputs`, so that strict parsing of duplicate members, prototype members and trailing text can be tested; the harness sends `rawInput` verbatim. An empty `reasonContains` in an expected rejection means the specification gives no wording and any non-empty reason is accepted. The generator compares its two runs per vector, because the whole file is larger than the 1 MiB canonical JSON bound. Writing the new vectors from the text exposed rules the text did not state; they were added to `docs/SPECIFICATION.md` and `docs/SCORING.md` and are pinned by `test/spec-field-rules.test.mjs`. The first 111 vector IDs and expected values are unchanged. Contract version 2 (ADR-0034) adds the `canonicalize`, `digest`, `verify-envelope` and `compare` operations and brings the file to 485 vectors (`kya.assessment-vectors/v2`); the 272 vectors of `assess` and `currency` described here are unchanged byte for byte.
