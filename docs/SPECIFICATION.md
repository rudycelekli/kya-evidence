# KYA Evidence specification, v0.1

Status: implemented experimental reference protocol. Independent security and standards-body review remain open. Normative requirements describe this implementation; they do not claim an adopted standard. Numbered requirements and their test traces are in [REQUIREMENTS.md](REQUIREMENTS.md).

## Purpose

Assess an exact agent configuration against a relying party's frozen policy for a declared scope, at a stated time. This is not human identity verification, an authorization grant, legal compliance, general safety or universal creditworthiness. `principal.id` is a pseudonymous controller reference. Never assign a person's creditworthiness or moral standing from this agent score.

The manifest declares; the profile freezes checks; receipts record outcomes; policy assigns trust and thresholds; assessment explains a decision. Keep declared, fixture-tested, runtime-observed and independently assessed evidence distinct.

## Records and bindings

| Record | Schema | Binding |
| :--- | :--- | :--- |
| Manifest | `kya.manifest/v1` | Agent, principal, full system, scope and validity interval |
| Profile | `kya.profile/v1` | ID, version, title and every frozen check/weight/critical flag |
| Policy | `kya.policy/v1` | Profile digest, scope, coverage/score/independence thresholds, optional mandatory minimums, source classes, freshness, trust anchors and revocations |
| Evidence | `kya.evidence/v1` | Subject, scope, profile, evaluator, run, check, artifact digest, outcome, source and validity interval |
| Assessment | `kya.assessment/v1` | Input digests, time, source mode, decision, score, dimensions, checks, rejections and limitations |
| Research universe | `kya.universe/v1` | All executable source bytes, package routing, frozen inputs/time, replayed assessment, source references, parent hypothesis and correction references |

Strict JSON rejects duplicate members, unsupported values, prototype keys, excessive resources and unknown schema fields. Canonicalization uses a bounded sorted-key JSON subset, not a claimed RFC 8785 implementation. SHA-256 digests are 64 lowercase hexadecimal characters. Timestamps are canonical UTC ISO strings.

The subject is the full-manifest digest. It binds harness/version, model, artifact/configuration digests, tool identities/versions/permissions and explicit scope. A manifest MAY declare `principal.accountableParty` as `{kind:'natural-person'|'legal-entity', ref}`, a pseudonymous reference to who answers for the agent; it admits no personal-data fields and an agent can never be its own accountable party. A policy MAY set `requirePrincipalBinding`; when true, a manifest without that declaration cannot qualify. The declaration is an unverified claim: it makes accountability inspectable and bound to the subject digest, and does not prove identity, authority or legal liability. Relying on an issuer's evidence never transfers the relying party's own accountability. Tool permissions must be allowed in scope. Allowed and forbidden permissions cannot overlap. Changing a manifest field creates a new subject and invalidates old evidence for it.

Records are digest-only and carry no personal-data fields. [PRIVACY.md](PRIVACY.md) describes the data flow, redaction before hashing and a scanner (`scripts/privacy-scan.mjs`); a clean scan is not evidence that no personal data is present.

### Canonical form and strict parsing

These rules were previously implied by the reference code and are now stated so that an implementation in another language can reproduce the bytes. They are a clarification, not a change: the reference already behaved this way (see CHANGELOG, Unreleased).

Parsing. The input is one Unicode text (a program reading bytes decodes UTF-8 and refuses ill-formed UTF-8; a text that holds an unpaired surrogate as a raw character is refused in the same way, whereas an unpaired surrogate written as an escape inside a string is accepted; the judgement is made on the decoded characters, so a high surrogate directly followed by a low surrogate is a pair however each was written) holding exactly one JSON value, optionally surrounded by whitespace. Whitespace is only space U+0020, tab U+0009, line feed U+000A and carriage return U+000D; a byte order mark, a no-break space and any text after the value are refusals. The grammar is RFC 8259 and nothing wider: no comments, trailing commas, single quotes, `NaN`, `Infinity`, hexadecimal, leading zeros, a leading `+`, `.5` or `5.`. A raw control character U+0000 to U+001F inside a string is refused. The only escapes are `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t` and `\u` with exactly four hexadecimal digits of either case; a valid surrogate pair of escapes denotes one character and an unpaired surrogate escape denotes one UTF-16 code unit and is accepted. Member names are compared after unescaping, so `"a"` and `"a"` are the same name; a name that occurs twice in one object is refused wherever it occurs. The names `__proto__`, `prototype` and `constructor` are refused at any depth.

Numbers. The value of a number is the IEEE-754 binary64 nearest to its decimal literal (ties to even), and the judgement is made on that value, not on the spelling. A value that is not finite (for example `1e400`) is refused. An integer-valued number whose magnitude exceeds 9007199254740991 is refused whatever its spelling (`9007199254740992`, `1e22`, `9007199254740993.0`). Every other finite number is accepted, so `1.0`, `1e2`, `0.5E1` and `-0` are accepted and `0.99999999999999999999` is the number 1.

Limits. The root value has depth 0 and a member or element has the depth of its container plus one; a value deeper than 32 is refused. More than 100000 values in total (every array, object, string, number, boolean and null counts once; member names do not) is refused, as is a string longer than 1048576 UTF-16 code units, an input longer than 1048576 UTF-8 bytes or a canonical form longer than 1048576 bytes.

Canonical form. No whitespace anywhere. An object is written with its members sorted by name in ascending order of UTF-16 code units (so a name holding a character outside the Basic Multilingual Plane sorts by its surrogate code units, not by code point), as `{`, `"name":value` joined by `,`, `}`. An array keeps its order. `null`, `true` and `false` are written literally. A string is written between double quotes with these escapes only: `\"` for U+0022, `\\` for U+005C, `\b`, `\f`, `\n`, `\r` and `\t` for U+0008, U+000C, U+000A, U+000D and U+0009, `\u00xx` for every other character below U+0020, and `\udxxx` for an unpaired surrogate code unit, in all cases with lowercase hexadecimal digits; every other character, including U+007F, U+2028, U+2029 and characters outside the Basic Multilingual Plane, is written literally. An integer-valued number is written as its decimal digits with a leading `-` when negative and without exponent, fraction or `+` (negative zero is written `0`). A non-integer number is written as the shortest digit string that converts back to the same binary64 value, in the form of ECMAScript Number::toString: a magnitude of at least `1e-6` is positional (`0.000001`, `0.1`, `123.456`), a smaller magnitude is one digit, an optional fraction without trailing zeros, `e-` and the exponent without padding (`1e-7`, `1.5e-7`). The canonical text is encoded as UTF-8 for hashing and signing.

### Digests and signing inputs

A digest is the lowercase hexadecimal SHA-256 of the UTF-8 bytes of a preimage. Digests of records are not domain separated: the preimage is the canonical form of the record, and the `schema` member inside the record is what keeps one record type from standing for another. Domain separation belongs to signatures: the signing input of a receipt is the text `kya.evidence/v1` followed by a line feed and the canonical form of the payload, and that of an incident record is `kya.incident/v1`, a line feed and the canonical form of its payload. The named artifacts are:

| Artifact | Value | Preimage | What it is called elsewhere |
| :--- | :--- | :--- | :--- |
| `manifest` | a manifest | canonical form of the manifest | the subject digest |
| `scope` | a manifest | canonical form of its `scope` member | `scopeDigest` |
| `profile` | a profile | canonical form of the profile | the value a policy holds as `profileDigest` |
| `policy` | a policy | canonical form of the policy | `policyDigest` |
| `evidence-signing-input` | a receipt payload | `kya.evidence/v1`, line feed, canonical payload | the bytes an evidence key signs |
| `incident-signing-input` | an incident payload | `kya.incident/v1`, line feed, canonical payload | the bytes an incident key signs |

A value that does not satisfy the field rules of its record type (below) has no digest: the digest of an invalid record is a refusal, not a digest of whatever was supplied.

### Envelope verification

A signed envelope is `{payload, proof}` and a proof is `{algorithm, keyId, publicKey, signature}`. Verifying an evidence or incident envelope applies these steps in this order and the first that fails names the failure code:

1. The envelope is not an object with exactly the members `payload` and `proof`: `MALFORMED_ENVELOPE`.
2. The payload does not satisfy the field rules of its record type (`kya.evidence/v1` or `kya.incident/v1`, whichever was asked for): `INVALID_PAYLOAD`.
3. The proof is not an object with exactly its four members: `MALFORMED_PROOF`.
4. `algorithm` is not the string `Ed25519`: `UNSUPPORTED_ALGORITHM`.
5. `keyId` is not a hash, or `publicKey` is not the one accepted spelling of an acceptable Ed25519 key: `INVALID_KEY`. The one spelling is `-----BEGIN PUBLIC KEY-----`, a line feed, the 60 base64 characters of the 44 byte SPKI (canonical padding bits, no wrapping), a line feed, `-----END PUBLIC KEY-----` and a final line feed. The 32 byte key must decode as an Ed25519 point per RFC 8032 section 5.1.3 and must not be a point of small order.
6. `keyId` is not the SHA-256 of the DER SPKI of the key: `KEY_ID_MISMATCH`.
7. `signature` is not exactly 86 characters of the base64url alphabet that decode to 64 bytes and re-encode to the same text: `INVALID_SIGNATURE_ENCODING`.
8. The signature does not verify under pure Ed25519 (RFC 8032) over the UTF-8 bytes of the signing input, with the scalar half required to be below the group order: `SIGNATURE_INVALID`. The equation checked is the cofactorless one of RFC 8032 section 5.1.7, `[S]B = R + [k]A` with `R` decoded as a point by section 5.1.3 (a `R` that does not decode is refused); a signature that satisfies only the cofactored equation `[8][S]B = [8]R + [8][k]A` is refused. (An earlier text said only "pure Ed25519 (RFC 8032)", which allows both; no vector pinned the choice.)

A valid envelope yields its `keyId`, its envelope digest (the digest of the whole envelope, proof included) and the SHA-256 of the signing input. Validity says only that the key made the signature over those bytes. It says nothing about whether the key is a trust anchor, its role, any revocation, or whether the payload concerns any subject; those are judged separately by policy, and a verifier MUST NOT treat a valid envelope as trusted.


## Trust and eligibility

Receipt outcomes are `pass`, `fail`, `abstain`, `error`. Sources are `runtime`, `fixture`, `declaration`; declarations never satisfy scored checks. A response cannot elevate fixture origin to runtime origin. An Ed25519 proof authenticates bytes and key possession, not truthful observation.

Trust anchors and `self`/`independent` roles come from an out-of-band relying policy. A receipt cannot make its own key trusted or assign itself independence. Organizational independence remains an external assertion. Revocation covers subject digests, evidence IDs and key IDs, using a supplied policy snapshot.

Eligibility requires a valid proof, trusted non-revoked key, matching subject/scope/profile/evaluator/check, allowed observed source and valid time. Future, pre-manifest, expired and overly old evidence is rejected. Rejection reasons remain in the report. Eligible duplicate evidence IDs are quarantined; invalid untrusted copies cannot quarantine an otherwise trusted receipt.

Assessor standing is advisory. A signed assessor disclosure (`kya.assessor-disclosure/v1`, [ADR-0028](adr/0028-assessor-disclosure.md)) lets a relying party check whether a key it assigned the `independent` role has declared and kept clear of conflicts, but it does not alter an assessment result and the criteria in [ASSESSOR-INDEPENDENCE.md](ASSESSOR-INDEPENDENCE.md) and [ACCREDITATION.md](ACCREDITATION.md) are drafts. Standing proves only that a key signed a disclosure, not that it is true.

A capture record (`kya.capture/v1`, [CAPTURE-CELL.md](CAPTURE-CELL.md), [ADR-0032](adr/0032-capture-cell-reference.md)) states what crossed a harness-owned tool boundary: the exposed tool surface, an ordered hash chain of calls and decisions, before and after digests of declared state, canary integrity, and bidirectional probe outcomes, signed by a capture-issuer key distinct from the evaluator key. The reference cell is simulated and claims no isolation. Evidence candidates derived from a verified capture are unsigned and carry source `fixture`; an evaluator key signs them. A capture proves what crossed a simulated proxy, not that a real agent is safe.

## Run selection and qualification

Only the latest whole run is selected. Checks cannot be mixed from several runs. Correctly bound trusted receipts establish recency before duplicate quarantine, expiry, freshness and revocation exclusions; invalidating a newer failure cannot revive an older pass. Tied latest runs create ambiguity and cannot qualify; a selected critical failure still blocks. A frozen run has one evaluator key and one observation per check. Repeated checks or mixed issuers cannot qualify it. Critical failure remains visible across observation timestamps. Successful retries require a fresh complete run ID. A check that has a quarantined duplicate-ID receipt in the selected run is unproven (status `unknown`), so replaying a failing receipt cannot let a sibling pass count toward the score. Independent capture is still needed to detect omitted entire runs; a proposed design is in [ADR-0017](adr/0017-measured-signed-capture-attestation.md) and [ADR-0020](adr/0020-external-anchoring-of-evidence-bundles.md) (not implemented).

Every frozen check stays in the denominator. Unknown, abstained and errored checks earn zero points and no observed coverage. Pass and fail count as observed; only pass earns points. Critical failure blocks; critical unresolved checks withhold qualification. Revoked or invalid-time subjects cannot qualify. At least one known pass/fail is required even when thresholds are zero. Coverage, independence and score thresholds then apply. See [SCORING.md](SCORING.md). A policy MAY name `mandatoryMinimums` (`{checkId, minimum}` with `minimum` `pass` or `independent-pass`); an unmet minimum caps the decision at `blocked` whatever the score, and a declaration or a removed observation cannot satisfy one. Every withheld or capped result carries a stable machine-readable code (`blockerCodes`, one per blocker); see [ADR-0016](adr/0016-named-blocker-codes-and-mandatory-minimums.md).

`validUntil` is bounded by the manifest expiry, selected receipts and policy age cutoffs. Reassess using fresh policy revocations before reliance. Revocation is not a live lookup service.

## Reports and viewers

The report includes input digests, full-scope `scopeDigest`, `selectedRunId`, `ambiguousRuns`, every check, `acceptedEvidenceDigests`, rejection reasons and explicit limitations. `scopeDigest` hashes the entire manifest scope, including purpose and permissions. A readable scope ID alone is insufficient for comparison. Legacy assessments must be recomputed before new exact-scope comparisons. `blockers` lists human-readable reasons and `blockerCodes` the stable code for each, index for index; reports without `blockerCodes` remain valid. `reportDigest` is an unsigned checksum. `verify` returns checksum integrity with `authenticated:false`; an attacker can checksum false claims. Recompute from trusted original inputs to assess assurance.

A relying party SHOULD run `checkCurrency` (CLI `kya currency`) before each reliance. It compares the assessment against the current manifest, policy and clock and fires `subject-changed`, `policy-changed`, `subject-revoked`, `assessment-expired`, `assessment-aged` (optional policy `maxAssessmentAgeSeconds`) or `clock-regression`; each trigger also carries a stable `code`. Any trigger means reassess. Validity ends at `validUntil`: the check time equal to `validUntil` already fires `assessment-expired`, consistent with `assess`, which rejects an expiry at or before its own time. It is the analogue of KYC ongoing monitoring for change events. It also accepts signed [incident records](adr/0014-signed-incident-and-appeal-records.md) (`kya.incident/v1`: report, resolution, appeal; digest-only, no narrative). A trusted unresolved high or critical report fires `incident-open`. Every distinct trusted report record is kept and a resolution may target a report only when exactly one report carries that ID, so duplicate or conflicting IDs fail closed. Only an independent policy-anchored key other than the reporter resolves a report, with a resolution dated strictly after it; a future-dated trusted blocking report stays open; and an appeal is recorded without clearing it. Ignored records are listed with reasons. It does not observe runtime behavior, an omitted incident is undetectable, and its result is unauthenticated. Continuous behavioral monitoring needs independent capture and remains open.

[Diagnostic dossiers](DOSSIERS.md) recompute the assessment and join originals to selected signed receipts. Replayed supported response predicates can support scoped strengths; signed assertions without matching originals remain reported passing claims. Failures preserve criticality without claiming a causal root cause. Missing telemetry, unresolved checks and seven structural observation limits remain visible. Standalone rendering validates consistency; trusted-input dossier verification recomputes the complete projection. Both remain unauthenticated without separate issuer/capture authority.

[Embedded benchmarks](BENCHMARKS.md) preserve 16 public fixture control cases and their complete expected populations. They challenge the evaluator and never measure commercial-agent competence or protected-holdout generalization.

The dashboard displays imported files as unverified claimed reports. Its presets use `kya.viewer-fixture/v1` and cannot masquerade as signed assessments. Raw observations and signed receipts are not embedded in the check list. Preserve authorized raw evidence privately, and redact before hashing public observation artifacts.

### Comparison of assessments

Comparing two assessments (`compareAssessments`, contract operation `compare`) takes a left and a right `kya.assessment/v1` report. Both are checked first, and a report that fails any check is refused outright, not reported as not comparable: the report checksum must match its content, the `blockerCodes` rules must hold (the code vocabulary and the cross-checks are those of [SCORING.md](SCORING.md): when `blockerCodes` is present each entry is one of the known codes listed there, the list has one code per entry of `blockers`, a `qualified` report has no codes, and unless a code `SUBJECT_REVOKED`, `SUBJECT_EXPIRED` or `SUBJECT_NOT_YET_VALID` is present the number of `CRITICAL_CHECK_FAILED` codes equals the number of check entries whose `critical` is `true` and whose `status` is `fail`; a check entry without a `critical` member is not critical for this count), and the report must carry `scopeDigest`, `profileDigest`, `evaluatorDigest` and `policyDigest` as hashes, a `scopeId` identifier, an `evidenceMode` of `none`, `runtime`, `fixture` or `mixed`, a `decision` of `qualified`, `insufficient-evidence`, `blocked`, `expired` or `revoked`, an integer `score.earned` and a `checks` array of entries holding an identifier `id`, an integer `weight` and a `status` that is a string (any string other than `pass` or `fail` makes the population incomplete, and a status of another type is a refusal); `blockers` must be an array whenever `blockerCodes` is present. A legacy report without a full-scope digest is therefore refused and must be recomputed.

Two valid reports are comparable only when all of these hold, tested in this order, and the first that fails is the reason code: `SCOPE_ID_DIFFERS` (`scopeId`), `SCOPE_DIGEST_DIFFERS` (the full-scope digest, so equal scope names with different purpose or permissions never compare), `PROFILE_DIFFERS` (`profileDigest`), `EVALUATOR_DIFFERS` (`evaluatorDigest`), `POLICY_DIFFERS` (`policyDigest`), `EVIDENCE_MODE_DIFFERS` (`evidenceMode`), `CHECK_POPULATION_DIFFERS` (the two `checks` arrays have different lengths, or differ in `id` or `weight` at some position, in order), `CHECKS_INCOMPLETE` (some check on either side has a status other than `pass` or `fail`). A comparable pair yields `scoreDelta` (right `score.earned` minus left), `decisionChanged` (the two decisions differ) and the fixed measurement text `same-policy evidence comparison; not a causal improvement claim`, together with both report digests. A comparison is not a claim that a change caused a score change.

### Currency result layout and reason vocabulary

A `kya.currency/v1` result has exactly these members: `schema`, `assessmentDigest` (the assessment's `reportDigest`), `checkedAt` (the check time as ISO UTC), `current` (true only when no trigger fired), `reliable` (`current` and the assessment decision is `qualified`), `action` (`reassess` when any trigger fired, else `none`), `triggers` (entries `{id, code, detail}` in firing order), `incidents`, `authenticated` (always false) and `limits`. `incidents` has `considered`, `open`, `resolved`, `appealed`, `observed` and `ignored`; the ID lists are de-duplicated and sorted, and `ignored` entries `{id, reason}` are sorted by `id` (null as empty) then `reason`. `limits` holds four fixed strings. Trigger detail strings are informational; branch on `code`.

Trigger firing order is: `clock-regression`, `subject-changed`, `policy-changed`, `subject-revoked`, `assessment-expired`, `assessment-aged`, `incident-open`.

Trigger `detail` strings feed the result digest and are fixed: `clock-regression` `Check time precedes the assessment time`; `subject-changed` `Manifest no longer matches the assessed subject digest`; `policy-changed` `Relying policy differs from the assessed policy`; `subject-revoked` `Subject digest is revoked by the supplied policy`; `assessment-expired` `Assessment validity interval has ended`; `assessment-aged` `Assessment is older than the policy maximum age`; `incident-open` `<n> unresolved high or critical incident record(s) for this subject`, where `<n>` is the decimal count of open incident IDs. The four `limits` strings, in order, are: `Detects change against supplied manifest, policy and clock only; it does not observe runtime behavior`; `Report checksum is unauthenticated; recompute from trusted inputs before reliance`; `Incident records are trusted only through the supplied policy anchors; an omitted incident is undetectable`; `A passing check is not an authorization grant`.

An assessment's `limitations` holds, in order, `Local policy result; not an authorization grant`, `Signatures attest bytes and key possession, not truthful execution` and `No universal predictive validation; public suites can be gamed`, followed by `Includes synthetic fixture evidence; not a real product benchmark` only when the evidence mode is `fixture` or `mixed`.

Reasons for `rejectedEvidence` entries (`{index, id, reason}`, sorted by `index`; `id` is null when the record never passed shape and signature validation, and is the record's own ID otherwise; because identifiers are at most 128 characters no cut applies to a valid record). A record gets the first reason that applies, in this order: a capture error text; any shape or signature failure text; `Signer is not a relying-party trust anchor`; `A capture-issuer key cannot issue scoring evidence`; `Subject is revoked`; `Subject is expired`; `Subject is not yet issued`; `Exact system digest differs`; `Evidence scope differs`; `Frozen profile differs`; `Evaluator digest differs`; `Evidence check is outside frozen profile`; `A declaration cannot satisfy an observed check`; `Evidence source is disallowed`; `Observation is in the future`; `Observation predates manifest`; `Signing key is revoked`; `Evidence is revoked`; `Evidence is expired`; `Evidence exceeds freshness policy`. After that, `Duplicate evidence ID`, `Equally recent run excluded; ambiguous runs cannot qualify`, `Older run excluded; checks cannot be mixed across runs` and `Superseded observation within selected run` apply to otherwise eligible records.

Recency of a run counts every receipt that was authentic and correctly bound, including revoked, expired and stale ones, so that invalidating a failure cannot resurrect an older pass. A receipt that fails any check before the `Observation is in the future` check, or that is itself future-dated or predates the manifest, never counts toward recency.

A run is as recent as the latest observation time among its bound receipts, and runs tie when those times are equal. The bound receipts are those that count toward recency: authentic, trusted, correctly bound, not future dated and not before the manifest, including any later rejected as revoked, expired or stale. The run rules are evaluated over them, not only over the receipts that remain eligible. A frozen run's issuers are the keys of the bound receipts of the selected run; a check is repeated when the selected run holds more than one bound receipt for it; an evidence ID is duplicated when more than one bound receipt in the whole bundle, in any run, carries it, and a duplicate inside the selected run raises `RUN_CONFLICT` and `RUN_INVALIDATED`. A receipt keeps the first reason in the order above even when it also takes part in one of these rules (an expired copy keeps `Evidence is expired`), and the other copies of a duplicated ID are rejected as `Duplicate evidence ID`. Revocation, expiry and freshness reasons apply to every bound receipt, including those of runs that are not selected, and they take precedence over `Equally recent run excluded` and `Older run excluded`.

Reasons for `incidents.ignored` entries: `Invalid incident record: <detail>` (id null), `Signing key is not a trusted anchor`, `Signing key is revoked`, `Incident concerns a different subject`, `Conflicting records share an ID; reports kept open, resolutions cannot target them`, `Conflicting records share one key and ID; not honoured`, `Incident is dated in the future`, `Blocking incident is dated in the future (clock skew or misdated); kept open`, `Ambiguous reference: several reports share this ID`, `References unknown incident`, `Resolution requires an independent trusted key`, `Reporter cannot resolve its own report` and `Resolution must be dated after the incident`.

Within the incident reasons, a record gets the first that applies in this order: `Invalid incident record`, `Signing key is not a trusted anchor`, `Signing key is revoked`, `Incident concerns a different subject`; a record that passes these is then judged by the shared-ID, future-date and resolution reasons in the order listed above. An exact duplicate record (same envelope digest) counts toward `considered` but is otherwise skipped and never listed.

Validator grammars: an identifier is 1 to 128 characters of the form `[A-Za-z0-9][A-Za-z0-9:._/-]*`; text is 1 to 512 characters, counted in UTF-16 code units (unless a field says otherwise), with no control character, where a control character is one of U+0000 to U+001F and U+007F (the characters U+0080 to U+009F are not control characters for this rule), except that a public key field holds a PEM SPKI public key of at most 2000 characters with line breaks and is validated by its own rule; a hash is 64 lowercase hexadecimal characters; a timestamp is the exact `YYYY-MM-DDTHH:MM:SS.mmmZ` form that round-trips through `Date#toISOString`.

Field rules (the reference validators enforce these; they were previously unwritten, so a second implementation had to guess them). A record has exactly the members its schema lists, no more and no fewer (the members, which an earlier text left to the reader of the field names below, are: a manifest has `schema`, `agent` (`id`, `name`, `version`), `principal` (`id` and optionally `accountableParty`), `system` (`harness`, `harnessVersion`, `model`, `artifactDigest`, `configDigest`, `tools`, each tool `id`, `version` and `permissions`), `scope` (`id`, `purpose`, `permissions`, `forbidden`, `approvalRequired`), `issuedAt` and `expiresAt`; a profile has `schema`, `id`, `version`, `title` and `checks`, each check `id`, `dimension`, `title`, `weight` and `critical`; a policy has `schema`, `id`, `scopeId`, `profileDigest`, `minCoverage`, `minIndependentCoverage`, `minScore`, `maxEvidenceAgeSeconds`, `allowedSources`, `revokedKeyIds`, `revokedSubjectDigests`, `revokedEvidenceIds` and `trustedKeys` (each anchor `id`, `role` and `publicKey`), and optionally `maxAssessmentAgeSeconds`, `requirePrincipalBinding` and `mandatoryMinimums`; an evidence payload has `schema`, `id`, `subjectDigest`, `scopeId`, `profileDigest`, `evaluatorDigest`, `runId`, `checkId`, `artifactDigest`, `outcome`, `source`, `observedAt` and `expiresAt`); a violation of any rule below refuses the whole input, except that an invalid evidence or incident entry is a rejection. Manifest: `agent.id`, `principal.id`, `principal.accountableParty.ref`, `scope.id`, every entry of `scope.permissions`, `scope.forbidden` and `scope.approvalRequired`, each tool `id` and each tool permission are identifiers; `agent.name` and `scope.purpose` are text of at most 512 characters; `agent.version`, `system.harness`, `system.harnessVersion`, `system.model` and each tool `version` are text of at most 128; `artifactDigest` and `configDigest` are hashes; `expiresAt` must be strictly after `issuedAt`. Each of those permission lists holds at most 256 unique entries; no `forbidden` entry is in `permissions`; every `approvalRequired` entry and every tool permission is in `permissions`; tool IDs must be unique and there are at most 128 tools. The accountable party `kind` is `natural-person` or `legal-entity` and `ref` differs from `agent.id` compared without regard to case. Profile: `id` is an identifier; `version` is text of at most 64 characters; there are 1 to 256 checks; a check `id` must be unique, its `dimension` is one of the six fixed dimensions `identity`, `authority`, `security`, `reliability`, `accountability` and `operations`, its `title` is text, its `weight` is an integer from 1 to 100000 and `critical` is a boolean. Policy: `id` and `scopeId` are identifiers and `profileDigest` is a hash; `minCoverage` and `minIndependentCoverage` are numbers from 0 to 1; `minScore` is an integer from 0 to 1000; `maxEvidenceAgeSeconds` and the optional `maxAssessmentAgeSeconds` are integers from 1 to 31536000; `allowedSources` holds at most 3 unique values from `runtime`, `fixture` and `declaration`; `requirePrincipalBinding`, when present, is a boolean; `mandatoryMinimums`, when present, holds 1 to 256 entries, each exactly `checkId` (an identifier) and `minimum`, and no `checkId` occurs twice; `revokedKeyIds` and `revokedSubjectDigests` hold at most 4096 unique hashes and `revokedEvidenceIds` at most 4096 unique identifiers; `trustedKeys` holds at most 256 anchors, each with a hash `id` that equals the SHA-256 of the DER SPKI of its key, a role of `self`, `independent` or `capture-issuer` and a unique `id`. Evidence: `id`, `scopeId`, `runId` and `checkId` are identifiers; `subjectDigest`, `profileDigest`, `evaluatorDigest` and `artifactDigest` are hashes; `outcome` is `pass`, `fail`, `abstain` or `error`; `source` is `runtime`, `fixture` or `declaration`; `expiresAt` is strictly after `observedAt`. Incident payload (`kya.incident/v1`; this paragraph was missing from earlier text and is a clarification): exactly the members `schema`, `id`, `subjectDigest`, `kind`, `severity`, `refId`, `reportedAt` and `detailsDigest`; `id` is an identifier; `subjectDigest` and `detailsDigest` are hashes; `kind` is `report`, `resolution` or `appeal`; `severity` is `low`, `medium`, `high` or `critical`; `reportedAt` is a timestamp; `refId` is `null` for a `report`, and for a `resolution` or `appeal` is an identifier different from `id`. A policy is validated on its own, so a `mandatoryMinimums` check ID is resolved against a profile only when an assessment is made, never when a policy is validated or digested. The reference tests pin these numbers in `test/spec-field-rules.test.mjs`.

Bindings that export an assessment into other ecosystems (in-toto, OpenTelemetry-style attributes, OAuth claims, SPIFFE, A2A and MCP metadata) are described in [INTEROP-BRIDGES.md](INTEROP-BRIDGES.md). They are unsigned, fail closed on non-qualified or non-current input, claim no conformance with the target specifications and have not been consumed by any third-party tool.

## Research replay and branching

[Universes](UNIVERSES.md) freeze all six assessment inputs including explicit time, current implementation inventory, computed report, question and source references. Forks clone inputs and name their parent and hypothesis. Verification recomputes the complete assessment under the matching archived implementation. Parent/correction graphs detect missing references and expose affected descendants; correction references remain declarations separate from revocation authority. Hash equality proves matching bytes, not who issued them, when they existed or whether observations were truthful. Comparisons require compatible complete populations and make no causal improvement claim.

## Interoperability and versioning

This is not an official implementation of Open-KYA, W3C VC, A2A or MCP. Credential/discovery bridges must preserve exact input digests, source class and limits. Compatibility needs executable multi-implementation tests. Alpha schema changes require explicit versioning and migration notes. Invalid top-level input fails; invalid individual receipts become rejections. Determinism requires frozen time and input files.

Claim-boundary codes classify the limit statements an artifact carries ([CLAIM-BOUNDARIES.md](CLAIM-BOUNDARIES.md), [ADR-0031](adr/0031-claim-boundary-codes.md)). A code states what the artifact does not show and never raises confidence. The registry (`evidence/claim-boundaries.json`) is append-only. Codes are not part of any record, digest or export; a producer MUST NOT omit or reword a limit statement because a code exists.

### Credential verification

A KYA assessment credential is a W3C Verifiable Credentials 2.0 data model document secured as a compact JWS (`vc+jwt`, algorithm `EdDSA`), and a status list is a second credential of the same kind. This subsection states how both are verified so that an implementation in another language reaches the same outcome (contract operation `verify-credential`). A valid result proves that the holder of the issuer key signed these bytes. It never says the agent ran truthfully, who a person is, or that anything is authorised, and a verifier reports `authenticated` as false in every case. Issuer trust is never inferred from a signature.

Inputs. `jwt`, the compact token; `now`, the time at which validity is judged (the verifier reads no clock); `expectedIssuers`, an array of strings that each begin `did:key:` (possibly empty); `policy`, a policy that satisfies its field rules, or null; `statusLists`, an object whose members map a status list URL to the compact token of that list, every value a non-empty string; `requireStatusCheck`, a boolean; `report`, a `kya.assessment/v1` object or null. Input of another shape (a `now` that is not a string, an `expectedIssuers` entry without the prefix, a policy that breaks its field rules, an empty list token, a report that is not an object) is refused.

Opening a `vc+jwt`. A token is opened by these steps in this order, and the first that fails names the single code of the result; nothing later is judged.

1. `now` is not a timestamp: `TIME_INVALID`.
2. The token is empty, or longer than 1048576 characters, or does not hold exactly two `.` separators, or its first or second segment is empty: `MALFORMED`. Each segment is unpadded base64url: only `A-Z`, `a-z`, `0-9`, `-` and `_`, and the decoded bytes must re-encode to the same text (so non-zero trailing bits are refused). The third segment, the signature, may be empty and then decodes to zero bytes. A segment that fails this is `MALFORMED`.
3. The first segment is decoded as UTF-8 (ill-formed UTF-8 is refused; a byte order mark is kept and so refused by the parser) and parsed by the strict parser of "Canonical form and strict parsing". A failure, or a value that is not an object, is `MALFORMED`. A header with a member written twice, including once as an escape (`"alg"` and `"alg"`), is therefore `MALFORMED`.
4. The `alg` member is not exactly the string `EdDSA`: `ALG_NOT_ALLOWED`. This is judged before any other header member, before the payload and before any key.
5. The header has a member other than `alg`, `typ`, `cty` and `kid` (so `jwk`, `jku`, `x5u`, `x5c`, `crit`, `b64` and every other name): `HEADER_MEMBER_NOT_ALLOWED`.
6. `typ` is not exactly `vc+jwt`, or `cty` is present and is not exactly `vc`: `TYP_NOT_ALLOWED`.
7. `kid` is not a string: `MALFORMED`.
8. The second segment is decoded and parsed the same way as the first; a failure, or a value that is not an object, is `MALFORMED`.
9. The payload has a member named `vc` or `vp`: `PAYLOAD_INVALID`. The payload is the credential itself.
10. The credential `issuer` is a string, or an object whose `id` is a string; that string is the issuer. Otherwise: `PAYLOAD_INVALID`.
11. The issuer is not a canonical Ed25519 `did:key`: `ISSUER_INVALID`. A canonical one is `did:key:z` followed by the base58btc text (Bitcoin alphabet; a leading `1` stands for a zero byte) of 34 bytes, which are the two bytes `ed 01` (multicodec ed25519-pub) and a 32 byte key. The text after `z` has 1 to 512 characters, the decoded bytes must re-encode to exactly that text, and the key must decode as an Ed25519 point per RFC 8032 section 5.1.3 and not be a point of small order. Any other multicodec, length or spelling is refused.
12. `kid` is not exactly the issuer, a `#`, and the issuer without its `did:key:` prefix: `KID_MISMATCH`.
13. The signature is not 64 bytes, or does not verify under pure Ed25519 (RFC 8032, with the scalar half below the group order) over the ASCII bytes of the first segment, a `.` and the second segment, exactly as given in the token, under the key of the issuer: `SIGNATURE_INVALID`.
14. `@context` is not an array whose first element is the string `https://www.w3.org/ns/credentials/v2`: `PAYLOAD_INVALID`.
15. `type` is not an array that includes the string `VerifiableCredential`: `PAYLOAD_INVALID`.
16. The payload has a member named `iss` that is not equal to the issuer string: `PAYLOAD_INVALID`.
17. `credentialSubject` is not an object (an array and null are not): `PAYLOAD_INVALID`.
18. `validFrom` is not a timestamp: `TIME_INVALID`. A `validUntil` member that is present, null included, and is not a timestamp: `TIME_INVALID`. A `validUntil` that is not strictly after `validFrom`: `PAYLOAD_INVALID`. An absent `validUntil` means no end.
19. `now` is before `validFrom`: `NOT_YET_VALID`. `now` is at or after `validUntil`: `EXPIRED`.
20. A member named `exp` that is not a number, or is a number with `now` at or after `exp` times 1000 milliseconds: `EXPIRED`. A member named `nbf` that is not a number, or is a number with `now` before `nbf` times 1000 milliseconds: `NOT_YET_VALID`.
21. `expectedIssuers` is not empty and no entry equals the issuer string: `ISSUER_NOT_EXPECTED`. When it is not empty and an entry equals it, the issuer trust is `expected`; when it is empty, `unchecked`.

Claims. A credential that opens is then checked against these rules, all of them, in this order, and each rule broken adds one entry (so a code can repeat). The subject is `credentialSubject`; the evidence block is element 0 of `evidence` (nothing when `evidence` is not an array or is empty).

1. The `type` array lacks `KyaAssessmentCredential`, or the subject `type` is not `KyaAssessment`: `PAYLOAD_INVALID`.
2. Each of `subjectDigest`, `profileDigest`, `policyDigest`, `evaluatorDigest` and `reportDigest`, in that order, that is not a hash: `PAYLOAD_INVALID`.
3. `evidenceMode` is not one of `none`, `mixed`, `runtime`, `fixture`, `declaration`: `PAYLOAD_INVALID`. Otherwise, when the mode is `fixture` or `mixed` and `limitations` is not an array holding the exact string `Includes synthetic fixture evidence; not a real product benchmark`, or when the mode is another one and `limitations` is such an array holding it: `EVIDENCE_MODE_LIMITATION_MISMATCH`. Both directions are errors, and a valid signature does not excuse them.
4. `limitations` is not a non-empty array: `PAYLOAD_INVALID`.
5. The subject `id` is not `urn:kya:subject:sha256:` followed by `subjectDigest`: `PAYLOAD_INVALID`.
6. The evidence block is missing, its `type` is not `KyaInputDigests`, or its `reportDigest`, `subjectDigest`, `profileDigest`, `policyDigest` or `evaluatorDigest` differs from the subject member of the same name: `EVIDENCE_REFERENCE_MISMATCH`.

Report binding. When `report` is not null, after the claims: a report whose checksum or blocker code rules fail is `REPORT_INVALID` and nothing further is checked against it. Only those two checks apply: the `schema` is `kya.assessment/v1` and the digest of the report without `reportDigest` equals `reportDigest`, and the `blockerCodes` rules hold (a report without a `blockerCodes` member is a legacy report and passes; when it has one, `blockers` must be an array and the codes must satisfy the rules of "Comparison of assessments"). The shape checks that comparison adds (scope digest, identifiers, check entries) do not apply here. A report that lacks any member that is copied into the rebuilt `credentialSubject` or evidence element (all of those listed below except `blockerCodes`, which may be absent) cannot be rebuilt from and is also `REPORT_INVALID`, `reportChecked` false. Otherwise the expected credential is rebuilt from the report. It has exactly these members: `@context`, the array of the context string above and `{"@vocab":"urn:kya:vocab:v1:"}`; `id`, `urn:kya:assessment:sha256:` and the report `reportDigest`; `type`, `["VerifiableCredential","KyaAssessmentCredential"]`; `issuer`, `validFrom` and `validUntil`, taken from the credential being checked; `credentialSubject`, with exactly `id` (`urn:kya:subject:sha256:` and `subjectDigest`), `type` (`KyaAssessment`), the report members `subjectDigest`, `scopeDigest`, `scopeId`, `profileId`, `profileDigest`, `policyDigest`, `evaluatorDigest`, `reportDigest`, `assessedAt`, `selectedRunId`, `decision`, `score`, `coverage`, `independentCoverage`, `evidenceMode`, `blockerCodes` (null when the report has no such member) and `limitations`, and `notAsserted`, which is `["human identity","authorization grant","truthful execution"]`; `evidence`, one element with `type` `KyaInputDigests` and the report members `subjectDigest`, `profileDigest`, `policyDigest`, `evaluatorDigest`, `evidenceBundleDigest`, `acceptedEvidenceDigests` and `reportDigest`; and `credentialStatus`, an array of the rebuilt entries, present only when the credential has entries. Each entry of the credential `credentialStatus` (a single value counts as a list of one, an absent or null member as none) is rebuilt as `{type: BitstringStatusListEntry, statusPurpose, statusListIndex, statusListCredential}`, with `statusPurpose` copied as given (the member must be present, with any value; an entry without it cannot be rebuilt), `statusListCredential` required to be a string that begins `http://` or `https://` and holds no white space character (the characters U+0009 to U+000D, U+0020, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000 and U+FEFF) and the index required to be a non-negative safe integer or a string of decimal digits, `0` or without a leading zero, of at most 16 digits (an integer is rewritten as its decimal string). When any entry cannot be rebuilt, `credentialStatus` differs and no entry is rebuilt. The status entries are issuer supplied and are not otherwise bound to the report. The credential and the rebuilt credential are compared member by member over the union of their top level member names by canonical text, an absent member equalling only an absent member. Each name that differs is a difference; so are `validFrom` not at or after the report `assessedAt` and `validUntil` not at or before the report `validUntil` (a missing or malformed report time counts as failing), named `validFrom` and `validUntil`. Any difference is `REPORT_MISMATCH`, and the sorted, de-duplicated list of differing top level names is reported. `reportChecked` is true only when the report was rebuilt from. Without a report a verifier checks internal consistency only: a holder of the issuer key can change the evidence mode, drop the fixture limitation or empty `notAsserted`, re-sign, and the credential still verifies.

Trust by policy. When `policy` is not null, the issuer key identifier is the SHA-256 of the DER SPKI of the issuer key. When no trust anchor of the policy has that `id`, or the identifier is in `revokedKeyIds`, the entry is `ISSUER_NOT_TRUSTED` and the issuer trust stays as opening left it (`unchecked` or `expected`) with the role null; otherwise the issuer trust is `anchored` and the issuer role is the anchor role. Trust is relative to the policy and to the expected issuers supplied, and `unchecked` says nothing was checked.

Status. Each element of the credential `credentialStatus` (an absent or null member means none, a single value counts as a list of one) is looked up in turn. A status list is present when the entry has a string `statusListCredential` that is a member name of `statusLists`; a name such as `toString` or a number never finds a list. An entry without a list is not checked and is reported with `checked` false and no error. An entry with a list is checked by "Status list check" below with the credential issuer as the only expected issuer. A failure is reported for the entry as `checked` false with the failure code, and adds one error whose code is the failure code when it begins `STATUS_` and `STATUS_VERIFICATION_ERROR` otherwise (`RANGE_ERROR` is reported in the entry as `RANGE_ERROR` and in `errors` as `STATUS_VERIFICATION_ERROR`). A checked entry with its bit set adds `REVOKED` (purpose `revocation`) or `SUSPENDED`; a set bit is not a failure of the check. The status is `checked` only when there is at least one entry and every entry had a list that passed the check. When `requireStatusCheck` is true and the status is not `checked`, `STATUS_NOT_CHECKED` is added last. The reported `purpose` of an entry is its `statusPurpose` when that is a string, else null.

Status list check. The list token is opened by the steps above, with the credential issuer as the only expected issuer (so a list signed by another key fails with `ISSUER_NOT_EXPECTED`). The mapping of opening failures is fixed: `EXPIRED` becomes `STATUS_LIST_EXPIRED`, and every other opening failure, including `NOT_YET_VALID` and `ISSUER_NOT_EXPECTED`, becomes `STATUS_VERIFICATION_ERROR`. The entry is judged first, by these rules in this order, each failure `STATUS_ENTRY_INVALID`: its `type` is `BitstringStatusListEntry`; its `statusListIndex` is a string of one to 16 decimal digits without a leading zero (`0` allowed); `statusSize` is absent or the number 1; `statusPurpose` is `revocation` or `suspension`. Then the token is opened. Then, in order: the list has no `validUntil`: `STATUS_LIST_NO_EXPIRY`; the subject `ttl` is present and is not a positive safe integer: `STATUS_VERIFICATION_ERROR`; `ttl` is present and `now` is at or after `validFrom` plus `ttl` milliseconds: `STATUS_LIST_EXPIRED`; the list is not of type `BitstringStatusListCredential` with subject type `BitstringStatusList`: `STATUS_VERIFICATION_ERROR`; the list `id` is not the entry `statusListCredential`: `STATUS_VERIFICATION_ERROR`; the list subject `statusPurpose` (a string or an array) does not equal or include the entry purpose: `STATUS_VERIFICATION_ERROR`. The `encodedList` is then decoded: it must be a string of at most 1048576 characters, begin with `u`, continue as unpadded canonical base64url, and be exactly one GZIP member (RFC 1952) with nothing after it (a second member and trailing bytes, zero padding included, are refused), whose CRC-32 and size trailer are correct and whose reserved header flags are clear, that inflates to at most 2097152 bytes; any failure is `STATUS_LIST_INVALID`. A list shorter than 131072 entries (16384 bytes) is `STATUS_LIST_LENGTH_ERROR`. An index at or beyond the number of entries is `RANGE_ERROR`. Otherwise the status bit is bit `index`, where index 0 is the most significant bit of byte 0 (the leftmost bit), and a set bit means the purpose applies.

Result. `valid` is true when no error was recorded. An opening failure reports its one code and leaves the issuer, trust, role and status null. Otherwise `errors` lists every code in the order recorded: claims, then report binding, then issuer trust, then status, then `STATUS_NOT_CHECKED`.

### Score card verification

A `kya.score-card/v1` is an unsigned, experimental card (label `KYA-SCR-EXPERIMENTAL`) that carries the per item results of repeated runs of one fixed item set, a manifest, and numbers computed from them. This subsection is the normative statement of the layout and the computation for the contract operations `verify-score-card` and `compare-score-cards`; it restates the layout section of ADR-0033, which stays Proposed. A valid card shows that the numbers follow from the embedded items and the manifest. It does not show that the named subject produced those items, that the items were unseen by the subject, or that the number predicts anything.

Encoding. A digest is the SHA-256, lowercase hexadecimal, of the canonical form ("Canonical form and strict parsing") of a value, and the limits of that section apply to every digest and canonical comparison below.

Top level. A card has exactly the members `schema` (`kya.score-card/v1`), `label`, `manifest`, `floor`, `runs`, `runDigest` (the digest of `runs`), `results`, `nonClaims` (the ten codes in this order: `NOT_PREDICTIVE_VALIDITY`, `NOT_CALIBRATED_TO_INCIDENTS`, `NO_INTER_ASSESSOR_AGREEMENT`, `NOT_SAFETY_CERTIFICATION`, `NOT_ENDORSED_OR_ADOPTED`, `NOT_A_PRODUCT_RANKING`, `INTERVAL_COVERS_ITEM_SAMPLING_ONLY`, `SUBJECT_IDENTITY_AS_DECLARED`, `OFFLINE_EXECUTION_NOT_VERIFIED`, `ITEM_SET_MAY_BE_MEMORIZED`) and `cardDigest` (the digest of the object holding every other member).

Manifest. Exactly `subject` and `suite` (each exactly `id`, `version`, `digest`), `evaluatorDigest`, `judge` (null, or exactly `id` and `digest`), `holdoutCommitment` (null, or a hash), `environment` (exactly `runtime`, a string of 1 to 128 UTF-16 code units, and `offlineDeclared`, a boolean) and `bootstrap` (exactly `seed`, a string of 1 to 128 UTF-16 code units, and `resamples`, an integer from 100 to 20000). Identifiers match `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`; every digest is 64 lowercase hexadecimal characters.

Floor. Exactly `minItems`, `minRepeats` and `minHeldOutItems`, safe integers not below 30, 3 and 10.

Runs. One to 32 runs with distinct identifiers matching the identifier pattern; each run has exactly `runId` and `items`, one to 2000 items with exactly `id` (an identifier), `outcome` (`pass`, `fail`, `abstain` or `error`), `heldOut` (a boolean), `durationMs` (a finite number from 0 to 1e9), `costUsd` (null, or a finite number from 0 to 1e6) and `canaryExposed` (a boolean; a builder may leave it out, meaning false, but a card carries it). Item ids are distinct inside a run. A builder, and a verifier rebuilding a card, sorts the items of every run in ascending order of `id` by UTF-16 code units; a card whose items are not in that order is not refused, it differs from its rebuild. Every run has the same ids and the same `heldOut` flag for each id.

Refusal to build. A card is not built when the item count `n` is below `minItems`, the run count `R` is below `minRepeats`, the held-out item count is below `minHeldOutItems`, or `holdoutCommitment` is null. The floor in a card can be higher than the minimums and never lower.

Generator. `seededRandom(seed)` is the SHA-256 of the bytes of the text `kya.score.seed/v1`, a line feed and the UTF-8 seed; words `a`, `b`, `c`, `d` are its first four big-endian 32-bit words. One step, with all arithmetic modulo 2^32: `t = a + b`; `a = b xor (b >> 9)`; `b = c + (c << 3)`; `c = rotl(c, 21)`; `d = d + 1`; `t = t + d`; `c = c + t`; the output is `t` as an unsigned word. This is sfc32 with `d` incremented before it is added to `t`, which differs from the published sfc32. Twelve outputs are discarded. `next(bound)` takes `limit = floor(2^32 / bound) * bound`, draws outputs until one is below `limit` and returns it modulo `bound`.

Member names of a result. An aggregate has exactly `items`, `repeats`, `score`, `ci95` (exactly `low` and `high`) and `resamples`, and no label. `outcomes` has exactly `pass`, `fail`, `abstain`, `error` and `denominator`. `repeatVariance` has exactly `perRunScores`, `mean`, `sd`, `min`, `max` and `unstableItemShare`. `cost` has exactly `totalUsd`, `knownItems` and `items`. `runtime` has exactly `totalDurationMs`, `meanPerRunDurationMs` and `maxItemDurationMs`. `integrity` has exactly `canaryExposures`. `results` has exactly `headline`, `heldOut`, `public`, `publicMinusHeldOut`, `outcomes`, `repeatVariance`, `cost`, `runtime` and `integrity`. The `version` members of `subject` and `suite` are identifiers.

Aggregates. For each item let `p_i` be the number of runs in which it passed. For a set of `m` items the aggregate has `items = m`, `repeats = R`, `score = floor(1000 * sum(p_i) / (m * R))`, `ci95` with `low` and `high`, and `resamples = B`. The bootstrap seed is the manifest seed, a vertical bar and one of `all`, `heldout`, `public`. It makes `B` resamples; each draws `next(m)` `m` times and sums the chosen `p_i`; the sums are sorted ascending; with `k = floor(B * 25 / 1000)` the low sum is entry `k` and the high sum is entry `B - 1 - k` (zero based), and `low` and `high` apply the score formula to those sums. `results` has `headline` (all items, label `all`), `heldOut` (held-out items, label `heldout`), `public` (the other items, label `public`, or null when there are none) and `publicMinusHeldOut` (null when `public` is null, else `public.score - heldOut.score`), then `outcomes`, `repeatVariance`, `cost`, `runtime` and `integrity`. `outcomes` has the count of each outcome over all runs and items and `denominator = n * R`, so abstain, error and fail are non-pass in a fixed denominator. `repeatVariance` has `perRunScores` (`floor(1000 * passes / n)` per run, in run order), `mean` (their arithmetic mean), `sd` (the square root of the sum over runs in run order of `(score - mean) * (score - mean)` divided by `R - 1`), `min`, `max` and `unstableItemShare` (the number of items whose outcome is not the same in every run, divided by `n`). `mean`, `sd` and `unstableItemShare` are rounded to 6 decimals as `round(x * 1e6) / 1e6`, where round takes halves toward positive infinity (the ECMAScript `Math.round`). `cost` has `totalUsd`, `knownItems` (the count of non-null `costUsd`) and `items = n * R`; `totalUsd` is null unless every item has a cost, else the sum of `round(costUsd * 1e6)` over all items divided by 1e6. `runtime` has `totalDurationMs` (the binary64 sum of every `durationMs`, in run order then item order, rounded to 3 decimals as `round(x * 1e3) / 1e3`), `meanPerRunDurationMs` (that unrounded sum divided by `R`, rounded to 3 decimals) and `maxItemDurationMs` (the largest). `integrity` has `canaryExposures`, the count of items with `canaryExposed` true over all runs.

Verification. A verifier works through these rules in order and reports problem codes. A value that is not an object, or whose `schema` is not `kya.score-card/v1`, gives only `wrong-schema`. A card with a member other than the nine top level members, or lacking one, gives only `unexpected-or-missing-fields`. Otherwise it adds, in this order: `card-digest-differs` (the digest of the card without `cardDigest` is not `cardDigest`); `run-digest-differs` (the digest of `runs` is not `runDigest`); `floor-below-hard-minimum` (the floor is not an object of exactly the three members each a safe integer at or above its minimum). The card is then rebuilt from its `manifest`, `runs` and floor (the minimums when the floor member is below them): a rebuild refused for the floor is `evidence-floor-not-met`, and any other failure of the rebuild (a malformed manifest, run or item) is `rebuild-failed`; the shape of the manifest, runs and items is judged before the floor, so a card that is malformed and below the floor is `rebuild-failed`. When the rebuild succeeds, `results-differ-from-recomputation` is added when the canonical text of the rebuilt `results` is not that of the card, and `card-differs-from-recomputation` when the canonical text of the whole rebuilt card is not that of the card. A failure of the verifier itself while doing this (for example a canonical form above its size limit) adds `unverifiable` to the problems already collected and the remaining steps are skipped. The card is valid exactly when no problem was added. A valid card yields its headline `score` and its `cardDigest`. Because every derived number and the order of `nonClaims` is recomputed, editing a number, an outcome, the seed, the resample count, the floor or a non-claim fails even when both digests are recomputed. A manifest member that no computation reads (subject, suite, evaluator digest, judge, a present commitment, the runtime text, the offline flag) is an operator statement: editing it and recomputing the digests gives a card indistinguishable from an honest one, and it verifies.

Comparison. Two cards are compared only when both are valid and their `manifest.suite.digest` and `manifest.evaluatorDigest` are equal. When either is invalid the result is not comparable with the single reason `card-invalid`; otherwise the reasons, in order, are `suite-digest-differs` and `evaluator-digest-differs`, and a pair with any reason is not comparable. A comparable pair yields `delta` (the left headline score minus the right) and `distinguishable`, true when the 95 percent item sampling intervals of the two headlines do not overlap (the high end of one is below the low end of the other). Distinguishable says nothing about validity or about variance between repeats, and a card is never a ranking of products.

The project's draft governance layer lives in [docs/governance](governance/CHARTER.md): charter, IPR policy, trademark and conformance-claim rules, versioning, extension registry and decision process. Each legal-style document opens with a draft-for-counsel notice and none has been adopted by any body. Requirements about these documents are checked by `test/governance-docs.test.mjs`. Regulatory crosswalks in [docs/crosswalks](crosswalks/README.md) are informative drafts: each carries the same notice, marks rows that rest on secondary sources, and makes no compliance claim; they are checked by `test/crosswalks.test.mjs`.
